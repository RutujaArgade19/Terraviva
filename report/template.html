WHAT THE MODEL CAN SAY

A useful harvest ledger.
A foundation for more.

The implemented depot records a product, a mass in tonnes, a field label and a date. That supports inventories of declarations and descriptive harvest summaries. The same fields do not supply the area needed for yield, the price needed for revenue, or the population coverage needed for market share.

Two questions guide this report: what is actually stored? And what can legitimately be calculated from it? The answers stay tied to the inspected code and to any file you choose to analyse.

↳

Preserve the grain when joining data.

A harvest row, a farm, a permission and an event are different units of analysis. Keep the farm identifier when concatenating exports. Count distinct farm IDs for cohort size; counting rows or permission objects will give a different answer.

The standard export

{
  "farm": "farm identifier",
  "records": [ /* harvest records */ ]
}

Grants, consent preferences, activity and pending actions are absent. This export is enough to inspect harvest declarations; it cannot establish permission for commercial reuse.

The analytical boundary

Confirmed declaration is the original row grain. One physical harvest can produce more than one declaration. No batch ID, parcel registry, crop-season identifier or measurement certificate establishes a stronger grain.

For a future normalized store, give farms, parcels, harvest events, source imports and grants stable identifiers. Keep quantities, dates, provenance and permission histories as separate concepts.

05 / DATA QUALITY & INTERPRETATION

Meaning comes before metrics.

01

Tonnes do not tell you yield.

Summing volume gives recorded mass. Yield needs an area denominator at the same crop, parcel and time grain. Revenue needs transactions, prices and currency. Market share needs a defined market and coverage.

MISSING DENOMINATORS
02

The date records intake, not necessarily harvest.

In the original SMS flow, the day comes from the server clock in UTC. Delayed messages and midnight boundaries can shift an apparent trend. A historical harvest date needs an explicit field and validation.

TIME SEMANTICS
03

A source label is not acquisition evidence.

The constant SMS label is also used for simulated and authenticated web submissions. Distinguish declared origin, actual acquisition channel, source-file identity and verification status.

PROVENANCE
04

Delivery duplicates and event duplicates are different.

Original message-ID deduplication protects retries. A new message describing the same harvest can still add another row. File imports need a stable identity strategy and visible conflict handling.

RECONCILIATION
05

Free text fragments categories.

Product labels are lowercased, but fields retain case and the SMS grammar rejects accents. Before benchmarking, establish crop codes, stable parcel IDs, unit conventions and correction history.

What classical EDA can establish

File shape, field coverage, observed ranges, category frequencies, exact duplicates, temporal support and descriptive associations. Each is conditional on the imported file and its measurement conventions.

What EDA cannot establish alone

Truth of a declaration, consent eligibility, causal effects, representative sampling, independent observations, fraud, anonymisation or production security. These require evidence beyond a plausible-looking table.

AGGREGATE ANALYTICS

Five farms is a threshold.
It is not a privacy proof.

The original aggregate helper suppresses results below five distinct consenting farms with records. Its UI supplies just one farm, so industry output is withheld. Small-group rules alone do not resolve dominance, location uniqueness or repeated-query disclosure.

Before a real aggregate product, define a cohort, prove eligibility from permission records, review disclosure risk and control repeated queries. A records-only export cannot prove consent.

VERSIONED BASE DATA

SQLite for the source snapshot.

The staging command creates a portable base.sqlite3 database with source-file checksums, table metadata and the original parsed rows. It also retains original files and produces a JSON catalog. Source values remain unchanged until an explicit transformation is justified.

One database file makes the base dataset inspectable with SQL and reproducible from the same inputs. Its tables describe the supplied archive; they do not invent farms, joins or ownership.

APP & LIVE DEPOT

JSON views, deliberate imports.

The app reads published JSON views from the dataset catalog. Each view retains provenance and identifies itself as reference data. Full tables that exceed the app’s stated limits require a split or another delivery method; they are never silently sampled.

Private farmer records and permission changes continue to use the encrypted live store. The SQLite snapshot is a versioned input, not a writable serverless database or a commercial-consent record.

↳

Reference data is not a farmer declaration.

Regional statistics or multi-farm records should remain reference datasets unless there is a valid mapping to a specific farm. Importing every archive row into the current farmer’s ledger would create a false account of that farm. The current catalog is explicitly empty because the requested ZIP has not been received.

Profiling conventions

  • Missing means absent, null, undefined or a whitespace-only string. Literal “NA”, zero and false remain data.
  • Numeric conversion is conservative. Identifiers and ambiguous local number formats are not treated as continuous measures.
  • Quartiles use linear interpolation on sorted values; standard deviation uses n − 1.
  • Outlier fences are Q1 − 1.5 × IQR and Q3 + 1.5 × IQR. No rows are removed.
  • Exact duplicates use original row values and deterministic object-key order. Business-event duplication is a separate question.
  • Correlations are Pearson r, pairwise complete, with n shown. Constant or insufficient pairs are undefined.
  • Date coverage requires recognizable, valid dates. No missing dates or quantities are invented.
Read scope, limits and reproducibility notes

All rows are profiled within the engine’s explicit file, row and column limits. Oversized inputs are refused instead of silently sampled.

Charts show the selected table; filtering the field dictionary does not filter observations. Correlation calculations may be bounded to a stated subset of numeric fields for wide tables. The imported source is never treated as representative of all farms. Dates and amounts require contextual interpretation.

For independent reproduction, preserve the original file and its checksum, parser settings, schema version and the report version. The full analysis engine is embedded in this HTML file. JSON profile export includes derived statistics and source metadata; category values can still reveal sensitive information.

The “Try a labelled example” fixture is created only to demonstrate report behavior. It includes a deliberate duplicate and missing field; its numbers are not evidence about Terraviva’s users, the hackathon archive or EU agriculture.

Rizz is used here as a writing and interaction discipline: clear meaning, visible evidence and recoverable controls. No charisma score or inferred scientific claim is attached to the design.
